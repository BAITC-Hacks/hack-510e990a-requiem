# EventMatch: инструкция команде

Репозиторий: https://github.com/BAITC-Hacks/hack-510e990a-requiem

Работаем в одном репозитории с двумя рабочими ветками. Обе ветки содержат весь проект, чтобы каждый мог запустить приложение самостоятельно. Переносить или удалять папки ради разделения не нужно.

## Ветки и три участника

| Участник | Ветка | Ответственность |
|---|---|---|
| Разработчик 1 — frontend | `frontend` | Форма, карточки, сообщения, адаптивность, взаимодействие страницы с API |
| Разработчик 2 — backend и AI | `backend` | Загрузка CSV, валидация, подбор, API, объяснения, подключение AI |
| Разработчик 3 — интегратор | `main` для проверки | Проверка Pull Request, объединение изменений, запуск по инструкции, сценарии защиты и документация |

Назначьте одного владельца каждой рабочей ветки. Каждый работает в своей локальной копии репозитория. Переключение ветки меняет файлы в текущей папке: не используйте одну общую папку одновременно для двух разработчиков.

`main` — версия, которую команда может показать жюри. Изменения приложения попадают туда через Pull Request (PR) после проверки интегратором. Это договорённость команды; автоматическая защита ветки и ограничения GitHub не настроены.

Если интегратору нужно исправить документацию, он создаёт короткую ветку от актуального `main`, например `docs/demo-guide`, и открывает отдельный PR. Такая ветка создаётся по мере необходимости, её сейчас нет. Исправления кода лучше вернуть владельцу соответствующей рабочей ветки.

## Начать работу: новый участник

Нужны Git, Node.js 22.12+ и доступ к репозиторию. Для отправки коммитов нужен доступ на запись. При отсутствии такого доступа попросите владельца GitHub-репозитория добавить вас в команду.

Склонируйте репозиторий и откройте полученную папку `hack-510e990a-requiem` в VS Code:

```sh
git clone https://github.com/BAITC-Hacks/hack-510e990a-requiem.git
cd hack-510e990a-requiem
git fetch origin
```

Если репозиторий уже есть на компьютере, клонировать его повторно не нужно. Откройте существующую папку в VS Code. Следующие команды выбора ветки выполняйте в её корне.

Frontend:

```sh
git switch frontend
git pull --ff-only origin frontend
```

Backend:

```sh
git switch backend
git pull --ff-only origin backend
```

После `git fetch origin` Git создаст локальную ветку из одноимённой удалённой, если локальной ещё нет. При ошибке `invalid reference` убедитесь, что используете нужный репозиторий и выполнили `git fetch origin`.

Интегратор:

```sh
git switch main
git pull --ff-only origin main
```

Перед переключением проверьте `git status`: незавершённую работу нужно сохранить в своей ветке. Не удаляйте чужие изменения и не используйте `git reset --hard` для устранения конфликта.

## Запуск в любой ветке

Из корня репозитория:

```sh
cd contractor-picker
npm ci
npm run dev
```

Откройте http://127.0.0.1:3000. Терминал с сервером оставьте работающим. Для Git-команд откройте второй терминал в корне репозитория. После изменения HTML/CSS/JS обновите страницу браузера; сервер автоматически перезапускается при изменении серверных файлов.

Для frontend тоже нужен этот сервер: страница обращается к `/api/meta` и `/api/recommend`. Не запускайте её через Live Server или открытие HTML-файла напрямую.

Без AI-ключа подбор работает с объяснениями по каталогу. Для реальной модели backend-разработчик локально настраивает `.env` по инструкции в README приложения. `.env` и `node_modules` не отправляем в Git. Коллеги устанавливают зависимости сами; ключ каждый хранит локально. Если ключа нет, сохраняем честную отметку режима без AI.

Если порт 3000 занят, остановите свой предыдущий сервер через Ctrl+C или укажите другой `PORT` в локальном `.env` и откройте этот порт в браузере.

## Договорённости между frontend и backend

Источник истины — [контракт API](contractor-picker/docs/api-contract.md).

- Frontend отправляет `budget` и `duration_hours` числами, дату — `YYYY-MM-DD`.
- Backend возвращает один из статусов: `matched`, `category_absent`, `no_matches`.
- Карточек не больше трёх; frontend сохраняет полученный порядок.
- Формат ответа включает `cards`, `counts`, `busy_contractors`, `query` и `explanation_mode`.
- Ошибка связи или сервера не показывается как «никто не подходит».
- Справочники запрашиваются из `/api/meta`, а не дублируются вручную.
- Нельзя переименовывать или удалять используемые поля без согласования. По возможности сначала добавляем новые поля, сохраняя старые, затем обновляем frontend.
- Если изменение ломает совместимость, оба PR объединяются согласованно после совместной проверки. До этого сохраняем работоспособность `main`.

## Приоритеты улучшений

Frontend: читаемые и различимые объяснения; понятные причины пустого результата; удобная форма; проверка мобильного экрана. Сохраняем отметки синтетических и проставленных данных. Дополнительные экраны и анимации — после основного сценария.

Backend: реальный AI-вызов после настройки ключа; проверка принадлежности фрагмента профилю; обработка таймаута и ошибок; корректная фильтрация занятости и ограничений; неизменный порядок одинаковых запросов. AI не решает, кто свободен, и не придумывает цены.

Интегратор: проверка запуска из чистой копии, согласование API, разбор PR, обновление сценария защиты и репетиция. Особое внимание объяснениям и воспроизводимости — они напрямую связаны с критериями оценки.

## Сохранить изменения и открыть PR

Сначала из папки `contractor-picker` выполните `npm run check` и проверьте затронутый сценарий в браузере. Затем из корня репозитория посмотрите `git status` и `git diff`.

Пример для frontend:

```sh
git add contractor-picker/public
git commit -m "Improve recommendation cards and empty states"
git push origin frontend
```

Пример для backend:

```sh
git add contractor-picker/server contractor-picker/tests
git commit -m "Improve recommendation explanations"
git push origin backend
```

Это примеры: добавляйте только реально изменённые файлы своей задачи. При согласованном изменении контракта или зависимостей добавьте соответствующие файлы отдельно. Сообщение коммита должно описывать сделанное изменение.

На GitHub откройте **Pull requests → New pull request**. Для frontend выберите `base: main`, `compare: frontend`; для backend — `base: main`, `compare: backend`. В описании укажите, что изменилось, как проверено и затронут ли API. Назначьте интегратора проверяющим. Не открывайте пустой PR: сначала в ветке должен появиться новый коммит.

Интегратор проверяет изменения и объединяет PR через **Create a merge commit**. Рабочие ветки `frontend` и `backend` не удаляем после слияния. Обычный merge сохраняет понятную историю для этих долгоживущих веток.

## Получить изменения коллег после слияния

Владелец рабочей ветки сначала сохраняет свою работу, затем из корня репозитория выполняет:

```sh
git fetch origin
git merge origin/main
```

Команда выполняется в своей ветке — `frontend` или `backend`, не в `main`. После успешного объединения и проверки отправьте обновлённую ветку: `git push origin frontend` либо `git push origin backend`.

Если изменился `package-lock.json`, снова выполните `npm ci` внутри `contractor-picker`, затем `npm run check` и проверьте затронутые сценарии.

При конфликте остановитесь и согласуйте итог с владельцем файла. В VS Code откройте конфликт, сохраните нужный результат, добавьте исправленный файл через `git add` и завершите merge командой `git commit`. Не используйте `git push --force` для общей ветки.

## Приёмка перед объединением

- Приложение запускается из `contractor-picker`; инструкция соответствует текущей версии.
- Повтор одного запроса сохраняет порядок карточек.
- Смена даты исключает занятых и объясняет причину.
- Отсутствующая категория и отсутствие совпадений явно различаются.
- Редкая категория не дополняется неподходящими профилями.
- Цена «от», max_hours=null и синтетические данные показаны честно.
- Реальный AI и резервный режим не выдаются друг за друга.
- В PR нет ключей, `.env` или `node_modules`.

Конкретные входные параметры и ожидаемые результаты: [сценарии защиты](contractor-picker/docs/demo-scenarios.md).
